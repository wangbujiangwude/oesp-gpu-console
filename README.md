## 1. 项目简介

这台设备出厂时 GPU（Mali-G52）和 VDEC 硬件解码器在系统里是"沉睡"的：
安卓容器跑在软件渲染上，视频播放走纯 CPU 软解，CPU 长期高负载。

本项目做了三件事：

1. **点亮宿主 GPU** —— 编译并加载主线 `panfrost` 驱动，屏蔽冲突的闭源 `mali_kbase`，
   得到 `/dev/dri/renderD128`，让安卓容器从 SwiftShader 软渲染切换到硬件渲染。
2. **把硬件解码器接到安卓媒体栈** —— 自研一个 **OMX IL 插件**，把 Linux 内核
   `meson-vdec`（V4L2 stateful M2M）包装成 Android 能识别的
   `OMX.meson.h264.decoder`，让 App 的 `MediaCodec` 能透明地用上硬解。
3. **做控制台** —— 一个飞牛 fnOS 原生应用（FPK），实时观测 GPU/硬解状态，
   20 项硬件体检，问题可一键修补。

**定位**：这是一个**个人硬件适配工程**，不是通用产品。它高度绑定特定 SoC、
特定内核、特定安卓容器镜像。

## 2. 核心价值与功能

### 2.1 唯一明确的正收益：3D 硬件渲染 ✅

| 项目 | 切换前 | 切换后 |
|---|---|---|
| 容器渲染器 | SwiftShader（软件） | **Mesa Mali-G52 (Panfrost)** |
| 中断线 | 无 | `panfrost-job` 正常触发 |

这是本项目**最实在、最无争议**的收益：UI 合成、游戏、WebGL 全部走 GPU，
CPU 从满负荷的像素搬运中解脱。

### 2.2 硬件解码：能跑通，但**当前架构下 CPU 反而更高** ⚠️

插件确实能让真实播放器走硬解（实测 `vdec` 中断 +197/8 秒，解码结果与软解
**逐字节相同**）。但性能对比的结论是**负收益**：

| 场景 | 硬解 | 软解 |
|---|---|---|
| 真实播放器，720p@25 | **1.39 ~ 1.49 核** | **0.86 ~ 0.88 核** |

即**硬解贵约 60%**。原因见 [6.1](#61-硬解在当前架构下是负收益)。

> 因为是负收益，控制台内置了**一键软/硬解切换**（v1.1.0）。默认可以按你的
> 实际场景选择 —— 想省 CPU 就用软解。

### 2.3 GPU 控制台功能

| 功能 | 说明 |
|---|---|
| 实时状态 | 3D 负载（用中断增长率代理）、硬解负载、GPU 频率、CMA 连续内存、温度、驱动模块 |
| 安卓容器面板 | 渲染模式（host/guest）、实际渲染器、设备节点、OMX 插件一致性 |
| **20+ 项硬件体检** | 宿主 H1–H10 + 容器 C1–C10 + 风险 R1 + 自愈 S1–S2，逐项给出问题与修法，并打分 |
| **一键修补** | 容器层（注入插件/修权限）、宿主层（modprobe/udev/自愈任务/自启动） |
| **常驻自愈** | cron 每分钟：插件注入、权限硬化、mediaserver codec 缓存刷新；另配完整性守卫，主脚本被断电截断时自动从备份恢复 |
| **一键切 GPU 直通** | 改 compose 并重建容器（会中断服务） |
| **软/硬解切换** | v1.1.0 新增，附实测数据说明 |
| 命令行查询 | `gpu_status.sh` 可在 SSH 直接用，不依赖 Web |

界面采用 fnOS 2.0+ 深色主题，中文。

## 3. 适用场景

### ✅ 适合

- 拥有 **Amlogic G12 系列**（S922X / S905X3 等）的飞牛 NAS，想让安卓容器用上 GPU
- 想搞清楚自己设备上 GPU / VDEC **到底有没有在工作**（可观测性）
- 愿意读日志、看数据、接受"实测可能推翻预期"的折腾型用户
- 需要把硬解能力接进安卓媒体栈做进一步开发（插件源码可直接复用）

### ❌ 不适合

- **非 Amlogic 平台**：控制台会自动降级，硬解插件完全不适用
- **想直接"装了就省 CPU"**：硬解部分是负收益，需要你自己切换权衡
- **生产环境 / 不能承受宕机**：本项目涉及 modprobe、容器重建、DTB 改动，
  且设备**没有硬件看门狗**，出错需物理断电
- **期待长期维护**：单人项目，见 [6.6](#66-维护状态)

## 4. 安装与运行

### 4.1 GPU 控制台（推荐，风险最低）

```bash
# 0) 获取源码（或直接下载 Release 里的 fpk，可跳过 1)
git clone https://github.com/wangbujiangwude/oesp-gpu-console.git

# 1) 打包（在 gpu-console 目录）
cd oesp-gpu-console/gpu-console && bash build_fpk.sh
# → ../gpuconsole_<版本>.fpk

# 2) 在飞牛设备上安装
appcenter-cli install-fpk gpuconsole_1.1.0.fpk -v 1
# 注意：同 appname 不会升级，需先 uninstall 再 install

# 3) （可选）授予宿主层修补所需的 root 权限，只需跑一次
sudo bash /var/apps/gpuconsole/target/scripts/grant_root.sh
```

打开飞牛桌面 → GPU 控制台即可。

> ⚠️ **不要用 `appcenter-cli restart`**（该子命令不存在），用 `stop` + `start`。

### 4.2 OMX 硬解插件（预编译产物，随包分发）

> **插件源码不在本仓库。** 控制台自带预编译的 32 位产物
> `gpu-console/scripts/libstagefrighthw32.so`，安装 FPK 后即位于设备上的
> `/var/apps/gpuconsole/target/scripts/`，控制台的「注入硬解插件」按钮直接取用它。
> 也就是说：**你不需要编译任何东西**，除非要改插件行为。

若确实需要自行构建（例如适配别的平台），流程如下 —— 但这部分源码需另行获取，
本仓库不提供：

```bash
# 1) 准备 Android NDK r26d（约 2 GB）
#    https://developer.android.com/ndk/downloads

# 2) 编译（源码目录结构：build_omx.sh + meson_omx_plugin.cpp + meson_vdec.h）
bash build_omx.sh
# → out/libstagefrighthw32.so   ★ 实际部署用这个（HAL 进程是 32 位）
# → out/libstagefrighthw.so     （64 位，仅参考）

# 3) 注入安卓容器
docker cp out/libstagefrighthw32.so <容器名>:/vendor/lib/libstagefrighthw.so
docker exec <容器名> chmod 644 /vendor/lib/libstagefrighthw.so

# 4) ★ 必须重启 mediaserver（它会缓存 MediaCodecList，只重启 media.codec 无效）
```

**验证是否真的走了硬解**（这是唯一可靠判据）：

```bash
# 宿主上读 vdec 中断，播放期间应增长（真硬解约 23~25 次/秒，为 0 即未走硬解）
awk '$NF=="vdec"{c=0; for(i=2;i<=7;i++) c+=$i; print c}' /proc/interrupts
```

## 5. 技术架构

```
┌────────────────────────────────────────────────────────────────┐
│ 飞牛桌面 / nginx                                                 │
│   /app/gpuconsole/*  ──── Unix Socket ────┐                     │
└───────────────────────────────────────────┼────────────────────┘
                                            ▼
┌────────────────────────────────────────────────────────────────┐
│ gpu-console/server/gateway.py   （单文件：HTTP 服务 + 前端 + 采集）│
│   /api/status  /api/detect  /api/repair  /api/decoder  /api/android │
└──────────┬──────────────────────────────────┬─────────────────┘
           │ sudo -n（经 grant_root 最小授权）  │ docker exec / cp
           ▼                                   ▼
┌──────────────────────────┐   ┌──────────────────────────────────┐
│ scripts/oesp_gpu_fix.sh  │   │ 安卓容器 androidemu-android       │
│  20 项检测 + 精准修补      │   │   MediaCodec → ACodec → OMX HAL   │
│  modprobe / udev / chmod │   │   media.codec（★ 32 位进程）        │
│  --decoder soft|hard     │   │        ↓ dlopen                    │
└──────────────────────────┘   │   /vendor/lib/libstagefrighthw.so  │
                               └──────────────┬───────────────────┘
                                              │ V4L2 ioctl
┌─────────────────────────────────────────────▼──────────────────┐
│ 宿主内核 meson-vdec → /dev/video0                                │
│   （依赖闭源 amlogic_codec_mm / media_clock / firmware 等模块）    │
└─────────────────────────────────────────────────────────────────┘
```

### 关键设计决策（以及为什么）

| 决策 | 原因 |
|---|---|
| **回答 `RequiresSwRenderer=1`** | 不回答时框架强制走 ANW/Surface，而容器 gralloc 的 `AHardwareBuffer_lock` 恒返回 `-38`，Surface 方案彻底不可用。回答后框架改用 ByteBuffer + 自带软件渲染器 —— **这是硬解能跑通的前提，也是负收益的根源** |
| **必须产出 32 位库** | 本机 `media.codec`（OMX HAL service）是 32 位进程，64 位库会被忽略 |
| **`flock` 用户态会话互斥** | 驱动只允许一个活跃会话（`cur_sess` 判据）。**并发两个会话会触发固件死锁**（见 6.4） |
| **内部 4 帧溢出环** | 让 CAPTURE 出帧与 App 供缓冲速度解耦，否则 App 落后 → 队列满 → 固件丢帧 |
| **不读 `/sys/class/vdec/*`、不开 `/dev/video26`** | 会导致整机死锁，见 6.3 |

## 6. 弊端与局限（务必读完）

这一节是本项目最重要的部分。以下每一条都有实测依据，**没有一条是谦虚客套**。

### 6.1 硬解在当前架构下是负收益

这是最核心、也最反直觉的结论。

| 对照 | 硬解 | 软解 |
|---|---|---|
| 真实播放器，720p@25 | **1.39 ~ 1.49 核** | **0.86 ~ 0.88 核** |

**为什么**：为了让真实播放器能跑起来，插件回答了 `RequiresSwRenderer=1`，
框架因此放弃 Surface 零拷贝，改走 ByteBuffer + 软件渲染器。代价是
NV12 数据要搬运两次、V4L2 syscall 开销重（实测 `sys 1.5s` vs `user 0.3s`）、
最后还要软件做 YUV→RGB。解码省下的算力被搬运全吃光还倒贴。
播放时宿主 `sy`（内核态）从 13.5% 冲到 31.7% —— 一半以上时间在内核搬运和 syscall。

**优化已经试过三项，全部无效**（这也是有价值的信息，它缩小了问题范围）：

| 优化项 | 结果 |
|---|---|
| `grabFrame` 逐行 memcpy → 整块拷贝（720p 每帧 1080 次小块拷贝 → 2 次） | **CPU 无变化**（1.49 vs 基线 1.50） |
| 零拷贝旁路溢出环（省每帧 1.38 MB 的一次拷贝） | **CPU 无变化**（1.48 / 1.39） |
| 主循环忙轮询 → 阻塞等待 | **直接卡死**，只出 3 帧后解码线程停摆 |

memcpy 优化零收益说明**搬运不是瓶颈**；等待直接卡死说明**主循环不能睡**。
剩下的只可能是 V4L2 缓冲在内核态的 cache 同步成本 —— **架构性的，用户态改不掉**。

> 补充一个容易误读的数据：用 `mctest`（ByteBuffer 基准）测时硬解 CPU 反而省
> 41~46%（720p：0.72s vs 1.22s）。但那不是真实播放器场景。
> **请以真实播放器的对照为准。**

**让硬解真正占优有两条路**，此前只看到第一条：

1. **Surface 零拷贝**（社区 `meson-vdec` 路线）—— 卡在容器 gralloc 的 `-38`，成本高；
2. **换用厂商 `amvdec_ports` 栈**（2026-10-05 新增）—— 它自带 `bypass_vpp` /
   `bypass_ge2d` / `enable_drm_mode` 参数，帧走 VDEC → VPP → ge2d → DRM dma-buf，
   **CPU 全程不碰像素**，正是电视盒子的做法。障碍是 `/dev/video26` open 死锁（雷区 #1）。

### 6.2 硬件能力天花板 —— ⚠️ 本节结论已于 2026-10-05 修正

> **本节此前写的「HEVC / AV1 硬件不存在」是错的，特此更正。**
> 那个结论来自社区驱动 `meson-vdec` 的 `VIDIOC_ENUM_FMT`，它只反映**社区驱动实现了什么**，
> **不反映硬件有什么**。详见 `docs/厂商解码栈开盖报告_2026-10-05.md`。

`meson-vdec`（社区驱动）的 `VIDIOC_ENUM_FMT` 实测：

| 格式 | 社区 `meson-vdec` | 硬件真实能力（厂商栈） |
|---|---|---|
| H.264 | ✅ 已打通 | ✅ `amvdec_mh264` |
| VP9 / MPEG1 / MPEG2 | ⚠️ 硬件支持，插件未接入 | ✅ `amvdec_vp9` / `amvdec_mmpeg12` |
| **HEVC / H.265** | ⛔ 社区驱动未实现 | ✅ **`amvdec_h265` 存在，未启用** |
| **AV1** | ⛔ 社区驱动未实现 | ✅ **`amvdec_av1` 存在，未启用** |
| AVS2 / AVS3 / VC1 / MPEG4 / MJPEG / H.266 | ⛔ 未实现 | ✅ 模块齐备，均未启用 |

**更正后的事实**：飞牛系统内已内置 **61 个 Amlogic 厂商驱动模块**
（`/lib/modules/$(uname -r)/updates/trim/amlogic-gx-vendor-drivers/`），
`vermagic` 与当前内核**完全一致**，其中 45 个格式/加速模块**从未被加载**。
微码 `/lib/firmware/video/video_ucode.bin`（1.6 MB）里内嵌了
`g12a_hevc.bin`、`av1_mmu`、`g12a_avs2_mmu.bin`、`gxl_mpeg12_multi.bin` 等全部格式固件。

**所以「HEVC 走不了硬解」不是硬件天花板，是「厂商栈没启用 + 我们一直在用社区驱动」**。
此前实测 HEVC 播放 `vdec` 中断为 0，是因为走的是 `meson-vdec`（`vdec` 中断线），
而厂商栈用的是另一套中断与内存路径。

**为什么厂商栈没启用**：飞牛官方在 `/etc/modules-load.d/meson-vdec.conf` 里写明
`# meson-vdec  # 禁用: 帧回传会挂死驱动`，并选择只启用 `galcore`。
厂商栈的 V4L2 入口 `/dev/video26`（`aml-vcodec-dec`）**open 即整机死锁**，
列入本项目五条致命雷区之首。这是当前唯一挡在厂商栈前面的障碍。

另有两类 App 即使对 H.264 也用不上硬解：
- **抖音**：使用自研 `libttffmpeg`，不走 `MediaCodec` → 劫持对它们无效
- **Chromium / VIA 浏览器**：主动选择 `OMX.google.*`，需要插件额外声明
  `COLOR_FormatSurface`（**未做**）

### 6.3 五条致命雷区 —— 操作失误会导致整机死锁

设备**没有硬件看门狗**，以下操作会让内核立即死锁，**只能物理断电**：

| # | 禁止操作 | 备注 |
|---|---|---|
| 1 | `open()` `/dev/video26` | 闭源 aml-vcodec-dec 固件死锁 |
| 2 | 读 `/sys/class/vdec/*` 任意节点 | **哪怕只是 `cat`** |
| 3 | `ffmpeg -c:v h264_v4l2m2m` 与软编混用 | — |
| 4 | 运行时 `rmmod` 闭源 GPU 驱动 | — |
| 5 | **并发创建两个 VDEC 会话** | 2026-10-04 实测触发死锁，导致一次断电 |

控制台与修补脚本**已主动规避**上述路径。若你要改代码，请阅读 `CONTRIBUTING.md` 第 1 节。

### 6.4 已知缺陷

| 缺陷 | 影响 | 状态 |
|---|---|---|
| **VDEC 会话引用计数只增不减** | 每次解码 +1，只能靠杀 `media.codec` 回收。实测 10 次会话 ref 3→13，**但不占内存、不影响解码正确性**（CMA 无泄漏），所以判定为无害计数器 | 已知，不修（重启进程即可回收） |
| **`SendCommand` 中 `cmdThread.join()` 同步死等** | 播放器 stop / 切换视频时会报 `failed to flush (err=-110)` 并重启一次解码组件 | **未修**（修法明确：改成单 worker + 命令队列） |
| **改 `media_codecs.xml` 切不到软解** | 实测改 name 或 type 后框架仍选中 meson 组件，必须移走 .so | 已知（控制台已用移走 .so 的正确方式） |
| **安卓容器升级会回退 GPU 直通** | 升级用包内模板覆盖 compose，`redroid_gpu_mode` 从 `host` 变回 `guest`，静默退回软渲染 | 需手动重跑修补 |
| **断电可能把文件截成 0 字节** | 2026-10-04 断电后自愈脚本被截断成空文件，cron 每分钟静默执行空脚本，**所有自愈能力失效且无任何日志** | 已加完整性守卫 |
| **CMA 长期偏低是正常现象** | 总 1204 MB（896+308），空闲常在 13~188 MB 波动。这不是泄漏，是内核 movable 页借用；实测 1080p 在空闲 65 MB 时仍能正常解码 | 非缺陷，勿误判 |
| **AVE-10 硬件编码未打通** | `encoder.ko` 可加载、微码存在于 `video_ucode.bin` 中，但 **DT 里没有设备节点**，probe 不触发。已编译好 U-Boot DT overlay 并部署，**但未启用**（需重启，风险自负） | 未启用，待验证 |
| **VPU / ge2d 闲置** | VPU 有驱动节点但闲置；ge2d 无 DT 节点不 probe | 未处理 |

### 6.5 环境与依赖限制

- **强绑定硬件**：仅验证于 Amlogic S922X / G12B。其它平台控制台会自动降级，
  硬解插件完全不可用。
- **依赖闭源内核模块**：运行期依赖厂商的 `amlogic_codec_mm`、`media_clock`、
  `firmware` 等。这些**不属于本项目、不随本项目分发**，也可能随系统更新变化。
- **依赖非标准安卓容器**：redroid 12 + privileged 模式。
- **构建需 2 GB 的 NDK**，且需手动下载（仓库不含）。
- **fnOS 应用环境限制**：`sys.executable` 为空串、PATH 不全（无 `/usr/sbin`）、
  `install_callback` 以应用用户而非 root 运行 —— 控制台已全部绕开，但这些
  限制意味着**换一个 fnOS 版本可能就要重新适配**。
- **容器重建风险**：切 GPU 直通会**重建安卓容器**，服务中断数分钟。

### 6.6 维护状态

- **单人项目**，2026-09-29 ~ 2026-10-04 密集开发约一周，此后节奏不稳定。
- 没有自动化测试、没有 CI。所有验证靠真机手工跑。
- 大量参数（预热帧数、缓冲数量、超时）是**针对这台设备调出来的经验值**，
  换设备大概率需要重调。
- 部分代码是"能跑就行"的探索性产物，**代码质量参差**，注释里记录了大量
  踩坑过程而非整洁的设计说明。
- 技术报告中包含若干**已被推翻的早期结论**（例如曾误判"CMA 被容器占满"、
  曾认为"并发测试无害"）。这些保留在 `docs/` 中作为过程记录，
  **请以最新结论和代码注释为准**。
