# 硬解能否用于安卓容器（redroid12 / androidemu-android）—— 实测报告

> 测试时间：2026-09-30 17:39–17:46
> 结论一句话：**容器层完全能用（零性能损失、字节级正确）；Android 框架层（App 的 MediaCodec）暂时用不了，缺 vendor codec HAL。**

---

## 一、被测对象

| 项 | 值 |
|---|---|
| 容器名 | `androidemu-android` |
| 镜像 | `redroid12_arm64`（Android 12） |
| Privileged | **true**（宿主 `/dev` 全部可见） |
| SELinux | **Disabled**（省掉 sepolicy 的麻烦） |
| 已映射设备 | `/dev/binder`、`/dev/dri`、`/dev/dma_heap` |
| 容器内可见 | `/dev/video0` (81,0)、`/dev/video26` (81,1)、`/dev/firmware_vdec` (273,100) |
| 启动状态 | `boot_completed=1`，`media.codec`(pid135)、`media.swcodec`(pid137) 进程均在跑 |

---

## 二、两层结论

### 第 1 层：容器层（Linux 进程视角）—— ✅ 完全可用

| 验证项 | 结果 |
|---|---|
| `/dev/video0` 容器内可见 | ✅ `crw-rw---- root video 81,0` |
| 静态 Linux 二进制能在 Android(bionic) 上跑 | ✅ 706 KB 静态 ELF 直接执行成功 |
| 容器内硬解吞吐（720p 500 帧 → /dev/null） | **1.972 s / 1.965 s = 254 fps** |
| 宿主同条件吞吐 | 1.974 s = 254 fps |
| **性能损失** | **0%（完全一致）** |
| 正确性（容器内 60 帧 vs 宿主 60 帧） | **字节完全一致**（`cmp` OK） |
| 正确性（容器内 60 帧 vs ffmpeg 软解 60 帧） | **字节完全一致**（`cmp` OK） |
| 端到端（500 帧写入 /data） | 499 帧，产物 689,817,600 B = 499×1382400 ✅ |

> 为什么静态 glibc 二进制能跑在 bionic 上：容器与宿主**共享同一个内核**，
> syscall ABI 一致，静态链接后不依赖任何 libc 运行时文件。
> 这是本方案能成立的技术前提，已实测而非推断。

### 第 2 层：Android 框架层（App 的 MediaCodec API）—— ❌ 用不了

`media.codec` 进程虽然在跑，但**没有任何硬件解码组件可供它加载**：

| 检查项 | 结果 |
|---|---|
| `/vendor/lib64/` codec 库 | 只有 `libstagefright_soft_*`（**全部软件**）、`libOmxCore.so`、`libstagefrighthw.so` |
| vendor OMX 插件（`libOMX.*.so`） | **无** |
| Codec2 HAL（`android.hardware.media.c2@1.x`） | **无** |
| `media_codecs.xml` 声明的硬件项 | **无**（只有模板占位 `OMX.foo.bar` 和 `OMX.redroid.h264.encoder`） |
| 实际生效的解码清单 | `media_codecs_google_video.xml` → 全是 `OMX.google.*` 软件解码 |

`libstagefrighthw.so` 是 OMX 硬件插件**加载器**，它需要 vendor 提供具体的
`libOMX.<vendor>.h264.decoder.so` 才能工作 —— 这个插件不存在。

**所以：App 调用 `MediaCodec.createDecoderByType("video/avc")` 拿到的仍是软件解码器。**

## 三、性能细节（有一个坑）

| 场景 | 耗时 | 有效吞吐 |
|---|---|---|
| 容器 → `/dev/null` | **1.97 s** | 254 fps |
| 宿主 → `/dev/null` | 1.97 s | 254 fps |
| **容器 → `/data` 落盘** | **7.70 s** | 65 fps（**慢 3.9 倍**） |

**慢的不是解码，是写盘。** 但注意这不是容器特有的问题：
- 容器内 `dd` 500 MB 写 `/data` = **307 MB/s**，比宿主的 285 MB/s 还快
- 可边解边写（690 MB）只有约 **90 MB/s** 有效速率

原因是解码器单线程 `fwrite` 小块 + 与取帧争抢，不是磁盘慢。
宿主演示也有同样现象（sys 时间从 1.47 s 涨到 6.34 s）。

> **工程建议：容器内一律用管道消费帧，别落盘。**

## 四、怎么用（已部署）

一键部署脚本已写好并跑通：

```bash
python run_many.py deploy_android_vdec.sh
```

它会：静态编译 → `docker cp` 到容器 `/data/local/tmp/vdec-dec` →
部署包装脚本 `/data/local/tmp/hwdec.sh` → 冒烟测试。

容器内调用：

```bash
# 进入容器
docker exec -it androidemu-android sh

# 硬解到文件（60 帧）
/data/local/tmp/hwdec.sh /data/local/tmp/in.h264 /data/local/tmp/out.nv12 60

# 硬解到管道，喂给消费程序（推荐，不落盘）
/data/local/tmp/hwdec.sh /data/local/tmp/in.h264 - 0 | <你的程序>

# 抽帧（在宿主做，容器只负责解码）
# 720p 紧凑 NV12，每帧 1382400 字节
```

`hwdec.sh` 内部固定了必需的三个环境变量（`PRELUDE_AU=2 TAIL_AU=1 COMPACT=1`），
不要去掉 —— 少任何一个都会导致首 GOP 亮度偏移或尾帧丢失。

## 五、⚠️ 新风险：容器里同样踩得到雷区

因为这个容器是 **Privileged=true**，宿主 `/dev` 全暴露，**致命节点在容器内也能看到**：

| 容器内危险节点 | 后果 |
|---|---|
| `/dev/video26`（81,1） | open 即整机死锁 |
| `/dev/firmware_vdec`（273,100） | 闭源固件加载口 |
| `/sys/class/vdec/*` | 只读 cat 也死锁 |

**在容器里 open 它们，和在宿主上一样会把整机搞挂（无看门狗，须物理断电）。**

### 建议的安全加固（可选）

把容器从 `privileged: true` 改成显式设备白名单，把危险节点排除掉：

```yaml
privileged: false
devices:
  - "/dev/binder:/dev/binder:rwm"
  - "/dev/dri:/dev/dri:rwm"
  - "/dev/dma_heap:/dev/dma_heap:rwm"
  - "/dev/video0:/dev/video0:rw"     # 只放行这一个
```

⚠️ 改动有风险：redroid 依赖 binderfs 等，去掉 privileged 后可能起不来。
**先备份现有 compose 文件再试**，起不来就立刻回滚。

## 六、如果想让 Android App 也用上硬解

三条路线，按成本排序：

| 路线 | 工作量 | 说明 |
|---|---|---|
| **A. 务实路线（推荐）** | 已就绪 | 容器内跑 Linux 进程解码，App 通过文件/管道/socket 取帧。适合抽帧、AI 分析、转码，不适合播放器实时渲染 |
| B. vendor OMX 组件 | 大 | 写 `libOMX.<vendor>.h264.decoder.so` 把我们的 V4L2 逻辑包进 OMX IL 状态机，再由 `libstagefrighthw.so` 加载，并改 `media_codecs.xml`。几百行 C++，还要对齐 redroid 的 OMX core 版本 |
| C. Codec2 HAL | 很大 | 实现 `android.hardware.media.c2@1.x` + `C2Component`；且 redroid 镜像未必带 c2/vndk 运行时 |

**推荐 A。** 需要播放器实时渲染时再考虑 B。

---

## 七、其他注意

- `/dev/video0` 是**独占**的：宿主和容器不能同时解码，并发会 `EBUSY`
- 容器内**没有 ffmpeg**（宿主有 8.1.1）。要在容器内消费帧，需自己 `docker cp` 一个静态 ffmpeg 进去
- `/data/local/tmp` 在容器重建后是否保留取决于 volume 配置，稳妥起见每次用 `deploy_android_vdec.sh` 重新部署
