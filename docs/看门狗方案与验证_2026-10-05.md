> 目的：解决「厂商解码栈 / VDEC 实验一旦触发内核死锁，只能人工物理断电」这个前置障碍。
> 有了看门狗，才有做后续解码栈实验的"退路"。

## 〇、先更正一个错误

上一份《厂商解码栈开盖报告》里写了
「已确认本机无 `/dev/watchdog`，硬死锁只能物理断电」—— **这句是错的**。
那次取证的输出被截断，我并未真正看到结果就下了结论。实际：

```
/dev/watchdog   (10, 130)
/dev/watchdog0  (244, 0) → /sys/devices/platform/soc/ffd00000.bus/ffd0f0d0.watchdog/
identity    = Meson GXBB Watchdog

timeout     = 30 s（可调，min 1）
nowayout    = 0
内核线程 watchdogd (pid 67) 已在跑；softdog.ko 也在
```

**结论：本机有 SoC 内置硬件看门狗，此前一直处于未启用状态。**

## 二、为什么这对解码栈实验是关键

死锁的三类，看门狗的有效性不同：

| 死锁类型 | 表现 | 硬件 WDT 能否救 |
|---|---|---|
| 用户态卡死 / 软锁 | 调度器还活着 | ✅ 能（喂狗进程停止 → 超时复位） |
| 内核 mutex 死锁（进程上下文） | 部分 CPU 卡住 | ✅ 能 |
| **spinlock + 关中断 / 总线挂起** | 整机无响应 | **理论上能** —— WDT 是 SoC 内独立硬件模块，走独立时钟，不依赖 CPU 执行指令；只要它的时钟还在跑，超时就发复位信号 |

第三类正是 `/dev/video26` 触发的那种。硬件 WDT 是**唯一不依赖人工断电**的复位手段
（本机无 BMC / IPMI）。

## 三、三级看门狗方案

### 第一级：SoC 硬件看门狗（已实现，待 firetest 验证）

`oesp_watchdog.py daemon --timeout 20 --interval 5`

- 常驻喂狗；SIGTERM 时写 `V` 优雅退出（不复位）
- 进程被 SIGKILL、或内核死锁导致本进程得不到调度 → 停止喂狗 → 20 秒后硬件复位
- 加 `--check` 还可做健康探测（fork + 读 `/proc/loadavg` + 关键 PID 存活），
  连续失败 N 次主动停止喂狗，提前触发复位而不是干等硬件超时

### 第二级：软件看门狗 `softdog.ko`（补充）

防"调度器还活着但系统已不可用"的情况，可作为第一级的补充触发 panic。
对硬死锁无效，不单独依赖它。

### 第三级：外部断电（真正 100% 兜底）

前两级都依赖 SoC 内部模块。若真出现连 WDT 时钟都停掉的极端硬件挂起，
唯一可靠的是**外部断电**：

- 一台独立于飞牛的设备（路由器 / 常开的 PC / 云主机）周期性探测飞牛心跳
- 连续 N 次失败 → 通过 **智能插座 / Wi-Fi 继电器** 断电 5 秒再上电
- 不依赖飞牛的任何软硬件状态，成功率取决于外部设备而非本机

本机已具备的网络条件：局域网可达（`<LAN_IP>`）、另有 frp 内网穿透可作外网通道。
需要额外购置：一个可控智能插座（约几十元）。

## 四、firetest：已验证，硬件真的会复位整机

`python3 oesp_watchdog.py firetest --timeout 20`：打开 → 喂 3 次 → **不写 V** 直接退出。

| | 执行前 | 执行后 |
|---|---|---|
| uptime | 45113 s | **147 s** |
| boot_id | `16f8a956-d321-4732-a756-c4887526965d` | **`e5d0d716-c2f3-45f1-aaa9-50165534fca8`** |

`boot_id` 改变、uptime 归零重来 → 确认是**硬件自己发出的复位**，不是断电。
**SoC 硬件看门狗可用，死锁后 20 秒自动复位，无需人工断电。**

### 已部署为常驻服务

`/etc/systemd/system/oesp-watchdog.service`（`enabled`，开机自启）：

```ini
[Service]
ExecStart=/usr/bin/python3 /usr/local/lib/oesp-gpu/oesp_watchdog.py daemon --timeout 20 --interval 5
Restart=always
RestartSec=3
```

实测状态：`state=active`、`timeout=20`、`timeleft` 持续在 15~17 之间被重置。

### 误复位验证：守护被杀不会拖垮系统

`kill -9` 守护进程 → systemd 3 秒后拉起（PID 45284 → 48728）→ 看门狗始终 `active`
→ uptime 246s → 269s 持续增长，**未重启**。

即：守护崩溃由 systemd 兜住，只有 **systemd 本身也跑不了的内核级死锁**才会触发复位。
这正是想要的行为。

## 五、第二、三级：外部兜底（用户已有智能插座）

SoC 内部看门狗已能覆盖绝大多数场景，但仍有一个理论盲区：
若死锁严重到连 WDT 模块的时钟都停掉，就只能靠**外部断电**。

### 关键前置：确认断电后能自动开机

ARM 盒子通常由 uboot 决定上电行为，多数默认上电即开机，但**必须实测**：
拔掉电源 → 等 10 秒 → 插回 → 看是否自动启动。
若不自启，需要改 uboot 环境或硬件跳线，否则外部方案无效。

### 接线与判定

```
常开探测设备（路由器 / 旧手机 / 树莓派 / 云主机）
    │ 每 10 秒探测一次飞牛（ICMP，或 TCP 22 / frp 映射端口）
    │ 连续 6 次（约 60 秒）无响应
    ▼
智能插座断电 5~8 秒 → 上电 → 飞牛自启
```

- **探测目标**：优先用局域网 `<LAN_IP>`；若探测端在外网，走 frp 的 `<WAN_IP>:<PORT>`
  （注意：这条链路本身依赖飞牛上的 frpc，飞牛死了 frp 也断，
  **所以外网探测要用"连不上即判定超时"的反向逻辑**，或优先用局域网探测）
- **判定要保守**：连续失败 6 次以上再动作，避免飞牛只是重启/升级时误断电
- **断电时长**：5~8 秒，确保电源彻底放电

### 插座接入方式（取决于品牌）

| 平台 | 接入方式 |
|---|---|
| Home Assistant | 直接调用 `switch.turn_off` / `switch.turn_on`，配自动化 |
| 米家 | 需 HA + `xiaomi_miot` 集成，或用米家 App 的"智能场景"（但无法由外部脚本触发） |
| 涂鸦 / Tuya | Tuya IoT 云平台 API（需开发者账号 + device_id），或 Local Tuya |
| 支持 HTTP/ MQTT 的固件 | 直接 `curl` 控制，最简单 |

## 六、对后续三项任务的影响

看门狗已就位，"有把握能退回"这个前提**已经满足**：

1. **三项代码级优化** —— 2026-10-04 已在社区栈上实测**全部无效**（整块 memcpy、
   零拷贝旁路均 CPU 无变化；空闲等待直接卡死）。重做意义不大，**真正的瓶颈是
   "帧必须回 CPU"这一架构选择**，不是用户态代码。建议跳过，直接做换栈。
2. **让硬解 CPU 低于软解** —— 必须换到厂商 `amvdec_ports` 栈（VPP + ge2d + DRM dma-buf）。
   有了看门狗，才敢去 modprobe 那些未加载的格式模块。
3. **docker 层统一调用解码器** —— 需要先有可用的解码栈，再在其上做统一调度层。

## 七、脚本用法

```bash
python3 oesp_watchdog.py status                  # 只读查看（零风险）
python3 oesp_watchdog.py selftest                # 验证 API（不会复位）
python3 oesp_watchdog.py daemon --timeout 20     # 常驻喂狗
python3 oesp_watchdog.py daemon --timeout 20 --check --pid <pid>   # 带健康检查
python3 oesp_watchdog.py firetest --timeout 20   # 验证真的会复位（会重启！）
```

部署为常驻（待 firetest 通过后）：写入 systemd unit 或加入现有 cron，
**必须在验证通过后**才开机自启，否则喂狗进程没起来反而会导致反复重启。
