# 相册视频「无法硬解 + CPU 高」实测报告

> 设备：OESP / Amlogic S922X (G12B)，飞牛 fnOS 内核 6.18.18-trim
> 容器：androidemu-android (redroid12_arm64)，gpu_mode=host，渲染器 Mesa Mali-G52 (Panfrost)
> 时间：2026-10-04 14:38 ~ 15:00（设备 11:55 重启后，本次未做任何破坏性操作）
> 被测文件：`/storage/emulated/0/Download/downloadfile.mp4`（用户 14:36 下载后在相册播放的那段）

---

## 一、结论先行

**1. 为什么没能硬解 —— 不是配置问题，是硬件天花板。**
这段视频是 **HEVC / H.265**（Main profile，1024x576，30fps，499 帧，16.63s，978 kbps）。
S922X 的 `meson-vdec` 硬件解码器 **不支持 HEVC**。实测 VIDIOC_ENUM_FMT 只有 `H264` / `VP90` / `MPG1` / `MPG2` 四种，
**HEVC 与 AV1 硬件不存在**。所以安卓框架只能选 `OMX.google.hevc.decoder` 软件解码。
铁证：播放期间宿主 `/proc/interrupts` 的 `vdec` 中断增量为 **0**。

**2. 一个反直觉的发现 —— 就算换成 H.264 走硬解，CPU 也不会降，反而升。**
把同一段视频转码成 H.264 后，硬解确实生效了（vdec 中断 +184~204 / 8s），但：

| 素材（完全同内容） | 解码组件 | vdec 中断/6s | media.codec CPU |
|---|---|---|---|
| HEVC 原文件（1024x576@30） | OMX.google.hevc 软解 | **0** | **1.14 核** |
| 转码 H.264（1024x576@30） | OMX.meson.h264 **硬解** | +184 | **1.49 核** |

同一文件、同播放器、同一台机器的干净对照（移走 OMX 插件强制回退，见附录）：

| 素材 hwtest30.mp4 (720p@25, 84s) | 解码组件 | vdec 中断/8s | media.codec CPU |
|---|---|---|---|
| A 组：插件在位 | OMX.meson.h264 **硬解** | +196 | **1.50 核** |
| B 组：插件移走 | OMX.google.h264 **软解** | 0 | **0.88 核** |

**硬解比软解贵约 70%。** 当前硬解路径在真实播放器里是**负收益**。

**3. CPU 到底高在哪**
播放 HEVC 时宿主侧采样：`media.codec`（omx@1.0-service）单进程占 **73%~96% 单核**（≈1 核），
系统态 CPU 从静止的 13.5% 冲到 **31.7%**，整机 busy 从 21.6% → 58.7%（6 核口径约多耗 2 核）。
`sugov:0/2`（CPU 调频内核线程）合计 ~80%，说明搬运/系统调用压力很大，而不是纯解码算力。

## 二、为什么硬解反而更贵

这是本次最重要的分析结论，直接决定是否还要在硬解上继续投入。

当前 OMX 插件为了绕开容器的 ANW/Surface 缺陷，回答了
`OMX_IndexParamVideoAndroidRequiresSwRenderer = 1`，
这会让 Android 框架放弃 Surface 零拷贝，改走：

```
VDEC → NV12 帧缓冲 →  memcpy 到 OMX IL buffer  → FillBufferDone
      → SoftwareRenderer 做 YUV→RGB → memcpy 上屏 Surface
```

解码算力的红利（项目历史数据：mctest 纯解码 720p 硬解 CPU 0.72s vs 软解 1.22s，省 41%）
被下面三笔开销全部吃掉并倒挂：

1. **NV12 的双次搬运** —— 每帧都要从 VDEC 缓冲拷到 IL 缓冲，再拷去渲染。
2. **V4L2 系统调用开销** —— 项目里已知的老问题：喂流线程 `sys 1.5s vs user 0.3s`，
   系统调用开销是用户态的 5 倍，在容器里 syscall 更贵（宿主 sy 占比本就偏高）。
3. **SoftwareRenderer 的 YUV→RGB** —— 硬解省下的那点算力在这里被重新吐出去。

**推论：不解决 Surface 零拷贝，硬解这条路在真实播放器里不可能带来 CPU 收益。**
而 Surface 的卡点是容器 gralloc —— `AHardwareBuffer_lock` 对外来缓冲恒返回 `-38 (ENOSYS)`，
且只会分配 RGBA。这条路目前是死的（除非换 gralloc 实现或改用别的 GPU 容器方案）。

## 三、CPU 高的构成（播放 HEVC 时，宿主视角）

```
%Cpu(s): 20.6 us, 31.7 sy,  41.3 id          <- 播放中
%Cpu(s):  8.1 us, 13.5 sy,  75.7 id          <- 停止后

播放中 TOP:
  omx@1.0-service (media.codec)   73~96%   <- HEVC 软解，约 1 核
  sugov:0 / sugov:2               42% 38%  <- CPU 调频内核线程，sys 压力指标
  surfaceflinger                  12.5%
  mediaserver                      8.3%
```

注意 **sy 从 13.5% → 31.7%**：系统态占比接近一半，说明大量时间花在内核搬运与 syscall 上，
而不是用户态解码运算。这也解释了为什么"换个更快的解码器"很难奏效。

## 四、顺带挖出的真 Bug（与本次现象无关，但会影响 H.264 播放）

日志里反复出现：

```
E/ACodec:        signalError(omxError 0x80001001, internalError -110)
E/MediaCodec:    Codec reported err 0xffffff92, actionCode 0, while in state 7/FLUSHING
E/NuPlayerDecoder: failed to flush [OMX.meson.h264.decoder] (err=-110)
E/NuPlayer:      received error(0xffffff92) from video decoder, flushing(2), now shutting down
W/NuPlayerDecoder: [OMX.meson.h264.decoder] failed to connect to native window, error=-32
```

`-110 = ETIMEDOUT`，是 ACodec 等 Flush 完成超时（约 10s）。

**根因（`meson_omx_plugin.cpp:1119`）**

```cpp
if (c->cmdThread.joinable()) c->cmdThread.join();      // ← 在框架调用线程里同步阻塞
c->cmdThread = std::thread(execCommand, c, Cmd, nParam1);
```

NuPlayer 停止/切换视频时会连发：`StateSet(→Idle)` 紧接着 `Flush(ALL)`。
第一条命令线程里跑 `stopDecoder()`，其中包含 `vdec.close()` 的排空 drain（DQBUF 排空到 LAST + STREAMOFF），
耗时不可控；第二条 Flush 就在这时 `join()` 死等 → 超过 ACodec 超时 → 播放器报错重启。

**修法**：SendCommand 不再 join 上一个命令线程，改为「单 worker 线程 + 命令队列」，
SendCommand 只入队并立即返回 `OMX_ErrorNone`（这也更符合 OMX IL 规范：SendCommand 只是投递）。
风险低、不需要动 V4L2 路径。**本次未改，等待确认后再动。**

## 五、建议（按 ROI 排序）

| 优先级 | 动作 | 预期收益 | 成本/风险 |
|---|---|---|---|
| **1** | **接受 HEVC 不能硬解**，改用 H.264 片源 | 播放同等画质 CPU 从 1.14 核降到……不会降（见 1.49 核那行）。**收益为负，不推荐** | — |
| **2** | **降低诉求** —— 降视频分辨率/帧率/码率，或降云手机串流的分辨率与帧率 | 立竿见影，线性降 CPU | 零风险，改设置即可 |
| **3** | 修 flush `-110`（改 SendCommand 为命令队列） | H.264 播放不再因 stop/切视频崩一次 | 低风险，需编译+部署 |
| **4** | 流水线化喂流，压 V4L2 syscall 开销 | 有可能让硬解重新压过软解（sys 1.5s vs user 0.3s 是现成的靶子） | 中工作量 |
| **5** | 攻 Surface 零拷贝（容器 gralloc lock 恒 -38） | **唯一能让硬解真正占优的路径** | 高，且依赖 gralloc/容器侧改造 |

**立即可做且零风险的**：降低串流侧的分辨率与帧率（还在 CPU 里洗澡的那部分），以及使用 H.264 低码率片源。

### 踩到的坑（下次别再犯）

- **改 `media_codecs.xml` 无法让框架改用软解**：把 `<MediaCodec name=... type="video/avc">`
  改成 `type="video/avc_disabled"` 或改 name 为 `.DISABLED`，kill mediaserver 后
  NuPlayer **仍然选中 `OMX.meson.h264.decoder`**（vdec 中断照涨）。
  可靠做法是把插件 .so 移走，让 OMXStore 根本注册不出该组件。
- **redroid 容器没有 `/tmp`**：`docker exec ... cp /vendor/etc/media_codecs.xml /tmp/bak`
  会报 `No such file or directory`，导致备份静默失败、实验窗口结束时无法还原。
  备份要用 `/data/local/tmp/`。本次已用 `/data/local/tmp/_xml.bak` 修正并从 `/root/vdec/omx/media_codecs.xml` 完成还原。
- 采样窗口要短于视频时长：先 `ffprobe` 确认 duration，避免视频播完后测到空转。
  本次 HEVC/转码 H.264 均为 16.63s，采样在 4~10s 区间，有效。
