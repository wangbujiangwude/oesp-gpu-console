| 问题 | 结论 |

## 二、闭源驱动清单：飞牛上到底有什么

全部位于 `/lib/modules/6.18.18.c997-trim/updates/trim/amlogic-gx-vendor-drivers/`（共 4530 个 ko 中的这些）：

### GPU（3D）

| 模块 | 身份 | 对 S922X 有用吗 |
|---|---|---|
| `mali_kbase.ko` (645KB) | ARM Mali **Bifrost** kbase driver，version `r21p0-01rel0`，alias `arm,mali-midgard`，license GPL | ✅ 对应 G52，但**我们已在用开源 panfrost**，3D 已正收益，不需要换 |
| `mali.ko` (453KB) | ARM Mali **Utgard** driver（Mali-300/400/450/470） | ❌ 老架构，与 G52 无关 |

`mali_kbase` 可调参数：`corestack_driver_control`、`scaling_dbg_level`、`gpu_dbg_level`、`override_l2_size`、`override_l2_hash`。
它暴露的调试能力（mmap/va_region/物理页分配）全部是 GPU 内存管理，**不含任何编解码能力**。

### 编码器（本轮目标）

| 模块 | 说明 |
|---|---|
| `encoder.ko` (104KB) | **AMLOGIC AVC Video Encoder Driver** — H.264 硬编核心 |
| `encoder_common.ko` (12KB) | description 实为 "Video Encoder **Bug Report** Driver"，纯日志辅助 |
| `jpegenc.ko` (99KB) | compatible `amlogic, jpegenc` — JPEG 硬编 |
| `amvenc_multi.ko` | ⚠️ 陷阱（多实例封装层），别用 |

`encoder.ko` 可调参数：`clock_level`、`encode_print_level`、`no_timeout`、`nr_mode`、`qp_table_debug`、`svc_enable`、`svc_ref_conf`、`use_reset_control`、`use_ge2d`、`dump_input`、`fixed_slice_cfg`。

### 解码器（顺带发现）

闭源栈**已加载**：`amvdec_ports`、`decoder_common`、`amlogic_codec_mm`、`media_clock`、`firmware`、`registers`、`stream_input`。
还有 `amvdec_h265`、`amvdec_vp9`、`amvdec_avs3`、`amvdec_h266` 等模块文件——但 `/dev/video26`（闭源栈产物）是**雷区 #1，open 即死锁**，不要碰。

## 三、encoder.ko 里到底写了什么（关键提取）

```
compatible        : "amlogic, amvenc_avc"      ← 注意逗号后有空格
设备名             : amvenc_avc                  → /dev/amvenc_avc
probe             : amvenc_avc_probe  ——  "probe start." / "probe end."
内存               : of_reserved_mem_device_init_by_idx + CMA pool
                     "check CMA pool success, max instance: %d"
                     "cma memory pool size: %d MB"
微码               : "avc encode ucode name is %s"
                     ucode_type_e: UCODE_GXL / UCODE_G12A / UCODE_TXL / UCODE_MAX
电源               : pwr_ctrl_psci_smc PDID_T3_DOS_HCODEC on/off   ← 标准 PSCI，非雷区
接口               : amvenc_avc_ioctl / amvenc_avc_compat_ioctl / amvenc_avc_poll
```

**依赖链（modinfo depends）**：
`media_clock, encoder_common, amlogic_media_compat_provider, amlogic_cpuinfo, decoder_common, registers, firmware, amlogic_codec_mm`

—— 其中 7 个**已经在内核里跑着**（被 amvdec_ports 拉起），只差 `encoder_common`。
这是本次最大的预期差：上次我判断"卡点很多"，实际依赖几乎是现成的。

## 四、★ 微码根本不缺（推翻旧结论）

`strings encoder.ko` 显示它要 **`ga_h264_enc_cabac`**，而系统里：

```
/lib/firmware/video/video_ucode.bin   1,636,608 bytes
```

是一个**多微码打包文件**，由已加载的 `firmware.ko` 解析（内含 `VIDEO_ENCODE`/`VIDEO_DECODE`/`VIDEO_PACKAGE` 类别）。
包内清单明确包含：

```
ga_h264_enc_cabac.bin     ← G12A/G12B 的 H.264 编码微码，正是 encoder.ko 要的
zga_h264_enc_cabac.bin
txl_h264_enc_cavlc.bin
gxl_h264_enc.bin
c1_jpeg_enc.bin / gxl_jpeg_enc.bin
```

旧记忆里"微码需要外部获取"是**错的**——它一直都在，只是不在 `/lib/firmware/meson/vdec/` 那个目录里。

## 五、注入 DT 节点：三条路全堵，第四条通了

| 途径 | 结果 |
|---|---|
| 内核模块调 `of_overlay_fdt_load()` | ❌ 符号**未导出**（kallsyms / Module.symvers 均无） |
| configfs overlay | ❌ configfs 已挂在 `/sys/kernel/config`，但**无 device-tree 子系统**（CONFIG_OF_CONFIGFS 未开） |
| overlay 用 `&label` 引用 | ❌ `__symbols__` **条目数 = 0** |
| **U-Boot `fdt apply`** | ✅ **可用** |

### U-Boot overlay 机制（`/boot` = vfat `/dev/mmcblk1p1`）

`/boot/fnEnv.txt`：
```
fdtfile=amlogic/meson-g12b-s922x-oes-plus-00050000.dtb
```

`/boot/boot.cmd` 关键段：
```sh
for overlay_file in ${user_overlays}; do
	if load ... ${prefix}overlay-user/${overlay_file}.dtbo; then
		fdt apply ${scriptaddr} || setenv overlay_error "true"
	fi
done

if test "${overlay_error}" = "true"; then
	echo "Error applying DT overlays, restoring original DT"
	load ... ${prefix}dtb/${fdtfile}     ← ★ 失败自动恢复原 DTB
fi
```

**这是安全网**：dtbo 有问题时 U-Boot 会重新加载原 DTB 并正常启动，不会卡死。

### phandle 速查（dtbo 里直接写数值即可，不需要 label）

| 对象 | phandle |
|---|---|
| clock-controller (clkc) | `0x02` |
| reset-controller | `0x05` |
| `linux,codec-mm-cma` | `0x3d` |
| `linux,codec-mm-reserved` | `0x3e` |
| power-domains | `0x03` |

### 已部署的 overlay

`/boot/overlay-user/amvenc.dtbo`（364 字节，fdtdump 校验通过）：

```dts
/dts-v1/;
/plugin/;
/ {
	fragment@0 {
		target-path = "/";
		__overlay__ {
			amvenc_avc {
				compatible = "amlogic, amvenc_avc";
				dev_name = "amvenc_avc";
				status = "okay";
				interrupts = <0x00 0x2d 0x01>;
				interrupt-names = "mailbox";
				memory-region = <0x3d>;
			};
		};
	};
};
```

设计依据：`vdec-legacy`（同类 BSP 驱动）节点**不含 clocks/resets 属性**，说明这套闭源驱动靠 `media_clock` 按名字自取时钟，DT 里不必写。预留了中断 45（`0x2d`）与 codec-mm-cma 作为内存池。

**当前 `fnEnv.txt` 未加 `user_overlays`，所以重启也不会生效——处于安全状态。**
备份：`/boot/fnEnv.txt.bak.20261004`、`/boot/fnEnv.txt.bak.amvenc`

## 六、已做的低风险验证

- `modprobe -n -v encoder` dry-run：只需补 `encoder_common` + `encoder` 两个模块
- 实际 `modprobe encoder_common` / `modprobe encoder`：**rc=0，系统存活**（uptime 正常）
- `lsmod` 确认 `encoder` 已加载，且 `firmware`/`media_clock`/`amlogic_codec_mm` 引用计数 +1
- `/sys/bus/platform/drivers/` 下出现 **`amvenc_avc`** —— 驱动已注册，只等设备
- 无 `/dev/amvenc_avc`（预期：无节点 → probe 未触发 → **尚未碰硬件**）

⚠️ 注意：probe 才是首次接触硬件（取时钟/复位/申请中断/加载微码），open+start 才会真正驱动编码器。
前一步风险低，后一步才是真正需要观察的地方。

---

## 七、后续路线与收益评估

若 probe 成功，完整链路还需要：

1. `/dev/amvenc_avc` 出现（Amlogic 私有 ioctl，**不是 V4L2**）
2. 用户态编码程序（参考 `aml_enc_test` 的 ioctl 序列，需自写）
3. 要喂给安卓容器 → 还得自写 **OMX 编码组件**（我们有解码组件的成功经验，但这是新工作量）

**收益点**：云手机串流目前是 scrcpy 抓屏 + **软件编码**，这是当前 CPU 消耗的大头。硬编若通，理论收益远大于硬解（硬解已被证明是负收益）。
**风险点**：闭源驱动实际编码时是否稳定未知；`vdec-legacy` 已声明中断 45 为 mailbox_2，可能与 encoder 争用。

## 八、待确认

唯一需要你拍板的是**是否启用 overlay 并重启**：

- 写入 `user_overlays=amvenc` 到 `/boot/fnEnv.txt` → 重启 → 查 `dmesg | grep amvenc` 与 `/dev/amvenc_avc`
- 会中断云手机/docker 数分钟（内网穿透 恢复另需 4~5 分钟）
- 回退：删掉 `/boot/overlay-user/amvenc.dtbo` 或把 fnEnv 改回备份即可，无需重刷系统
