## 一、测试方法与口径（先讲清楚，避免误读）

| 项目     | 做法                                                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------------------------------- |
| 输入素材   | ffmpeg `testsrc2` 生成 300 帧 / 12 s / 25 fps 的 H.264 Annex-B（1080p、720p）；4K 用 **25 帧小样本**（避免大缓冲触发内存压力复位）                  |
| 硬解     | `/usr/local/bin/vdec-dec`（V4L2 `meson-vdec`），`PRELUDE_AU=2 TAIL_AU=1 COMPACT=1`，输出 **`/dev/null`**（剔除磁盘/tmpfs 变量，纯解码口径） |
| 软解     | ffmpeg 8.1.1；`-f null`（只解码）与 `-pix_fmt nv12 -f rawvideo /dev/null`（**同工作形态**：解出 NV12）                                   |
| 编码     | `avetest10`（dlopen 设备版 `libvpcodec.so`，真实 ABI），60 帧**纯 `enc()` 计时**（不含落盘）；对照为 x264 编码**同一份 NV12 输入**                    |
| CPU 口径 | bash `time` 的 `user + sys`；`core_equiv = (user+sys)/real`（整机 6 核，故 1.0 = 1 核当量）                                         |

> ⚠️ 本报告只测**本机自己的硬件通路**：解码 = `meson-vdec`（主线 staging 驱动），编码 = AVE/HCODEC（厂商 `encoder.ko` + 运行时修复）。  
> 与容器内 OMX、飞牛影视转码是不同链路，不要混用数字。

## 二、解码实测

### 2.1 硬件解码（meson-vdec，输出 `/dev/null`）

| 分辨率           | 轮次结果（fps）                           | 稳定档             | 工具内部耗时                | 像素吞吐（稳定档）       |
| ------------- | ----------------------------------- | --------------- | --------------------- | --------------- |
| 1080p（302 AU） | 39.6 / **118.1** / **118.5** / 40.4 | **118 fps**（快档） | 2.27 s                | **≈ 244 Mpx/s** |
| 720p（302 AU）  | **197.7 / 199.3 / 195.3**           | **≈ 198 fps**   | 1.29 s                | ≈ 183 Mpx/s     |
| 4K（27 AU）     | 4.4 / **18.4** / 4.3                | 不稳定             | 0.94 s（快档）/ 5.7 s（慢档） | 18–145 Mpx/s    |

- **双模态现象**：同一二进制、同一输入、同一参数，1080p 在 **40 fps 与 118 fps** 两档之间跳（4K 在 4.4 与 18.4 之间跳），720p 则稳定。比值约 3×（1080p）/ 4×（4K），与「CMA 缓冲分配 / 容器负载竞争」高度相关，**不是驱动错误**（每次 rc=0、输出完整）。
- **性能模型**：稳定档约 **200–250 Mpx/s**，与历史报告（09-29/30 空载：720p 254 fps、1080p 128 fps、≈250 Mpx/s）一致 ⇒ 本次双模态的低档是**环境干扰**，高档才是器件真实能力。

### 2.2 软件解码（ffmpeg / libavcodec，同机）

| 分辨率      | 转 NV12 输出    | 只解码（`-f null`） | CPU（core_equiv）                |
| -------- | ------------ | -------------- | ------------------------------ |
| 1080p    | **89.4 fps** | 123 fps        | **2.98 核**（转 NV12）/ 2.66 核（丢弃） |
| 720p     | 160.2 fps    | —              | —                              |
| 4K（25 帧） | 21.5 fps     | 28.3 fps       | 1.88 核                         |

### 2.3 硬解 vs 软解（1080p，转 NV12 同工作形态）

| 指标  | 硬解           | 软解            | 结论                |
| --- | ------------ | ------------- | ----------------- |
| 吞吐  | 118 fps（快档）  | 89 fps        | 硬解快 **1.3×**      |
| CPU | **0.92 核**   | **2.98 核**    | 硬解省 **3.2×** CPU  |
| 质量  | —            | —             | **逐字节相同**（见 2.4）  |
| 4K  | 4–18 fps（不稳） | **21–28 fps** | 4K 场景**软解反而更稳更快** |

### 2.4 正确性：与软解**逐字节相同**

1080p 取前 40 帧，硬解输出 NV12 与 ffmpeg 软解输出 `cmp` ⇒ **BYTE_IDENTICAL**（Y_MAE = 0）。  
硬解不是「近似」，是**无损等价**通路。

### 2.5 波动来源（诚实标注）

`vdec-dec` 用户态框架把每帧从 mmap 缓冲**拷出**（1080p 每帧 3.1 MB），CPU 主要花在这个 copy 上（慢档 sys 5.8 s / real 7.7 s）。  
因此当云手机容器抢占 CPU（本轮 docker 400%、lmkd 90%、logd 80%）时，硬解**框架侧**会掉速——**掉的是拷贝，不是解码**。  
若把解码直接接到编码器/显示管线（零拷贝），抖动预计显著收敛（见第六节建议 3）。

## 三、编码实测（AVE / HCODEC）

### 3.1 AVE 硬编（60 帧纯 `enc()` 计时）

| 分辨率                   | 帧耗时     | 等效 fps               | 输出码率      | CPU（core_equiv） |
| --------------------- | ------- | -------------------- | --------- | --------------- |
| 640×360               | 7.99 ms | **125.2 fps**        | 11.6 Mbps | ≈0.16 核         |
| 1280×720              | 29.0 ms | **34.5 fps**         | 45.2 Mbps | ≈0.16 核         |
| 1920×1080（fps 配 25）   | 62.8 ms | **15.9 fps**         | 105 Mbps  | ≈0.18 核         |
| 1920×1080（fps 配 60）   | 33.4 ms | **29.9 fps**         | 263 Mbps  | ≈0.14 核         |
| 2560×1440 / 3840×2160 | —       | **不可用**（`ok=0` 优雅失败） | —         | —               |

- **上限 = 1080p**：1440p/4K 全部优雅失败（返回失败，不挂死，安全）。
- **fps 配置影响速度**：同分辨率 fps=60 配置比 fps=25 配置**快约 2×**（62.8 → 33.4 ms），机制未明（疑与硬件按配置帧周期流水有关）。
- **零 CPU 是真实卖点**：整机 CPU 占比 2.4–3.1%（0.14–0.18 核），其中还含测试程序自身的开销。

### 3.2 同内容对照（同一份 60 帧 1080p NV12）

| 编码器                      | fps      | 输出体积                   | CPU    |
| ------------------------ | -------- | ---------------------- | ------ |
| **AVE 硬编**（br=4M）        | **15.9** | **32.9 MB**（≈110 Mbps） | 0.18 核 |
| x264 ultrafast `-b:v 4M` | **42.3** | 2.6 MB                 | 2.61 核 |
| x264 ultrafast CRF       | 34.2     | 7.3 MB                 | 2.08 核 |
| x264 veryfast `-b:v 4M`  | 13.3     | 1.55 MB                | 2.64 核 |
| x264 medium `-b:v 4M`    | 5.5      | 1.20 MB                | 2.11 核 |

⇒ **吞吐型转码请用软件编码**（ultrafast 是 AVE 的 **2.7×**，且体积只有 1/12）；AVE 的唯一优势是**不占 CPU**。

### 3.3 码率控制失效（三层定性）

| 层        | 结论              | 证据                                                                                                         |
| -------- | --------------- | ---------------------------------------------------------------------------------------------------------- |
| 用户态参数链   | ✅ 参数真的被消费       | `vl_encoder_param_t` 按值打包进 x3/x4；`bitrate → handle+0x48`；rodata 实证 `rate_control = AVC_ON` 默认开             |
| 用户态 rc 表 | ⚠️ 被「剥坑」，可运行时重接 | `gx_fast_rc` 5 个函数指针的 RELATIVE 重定位 addend **全被清 0**（代码保留、指针断开）；`grc` 符号导出 ⇒ 自研 `RCFIX` 已能重接，重接后仍无效         |
| 内核       | ❌ 当前边界          | QP 经 `FASTGX_AVC_IOC_NEW_CMD` 的 `control_info[6]` 下发，**`encoder.ko` 无视 QP**（帧 0 quant=30 仍产出 2.24 bpp 近无损） |

实测验证：BR = 1M / 4M / 8M → 输出 113.6 / 109.8 / 110.2 Mbps（**几乎无差异**）。  
⇒ 只要不解决内核侧，**输出恒为近无损大码流**。

### 3.4 产物质量

AVE 输出为标准 **Annex-B H.264（Main profile）**，ffmpeg 解码 **60/60 帧无错**；54 批以来所有样本均可解。

## 四、稳定性与运维（本轮真实发生的事）

### 4.1 ✅ 「重启后自愈」验收通过（此前唯一未验证项，现已闭环）

本轮设备发生两次非计划冷启动，恰好构成真实验收：

| boot_id    | 冷启动 → 修复应用         | 结果                                                             |
| ---------- | ------------------ | -------------------------------------------------------------- |
| `87aaff8b` | boot 后 **+30.4 s** | cron 自动应用：4 项 VALIDATE 全 MATCH、`FIX OK — codec_reg path alive` |
| `159798c5` | boot 后 **+39.3 s** | 同上，全 MATCH                                                     |

- **零人工介入**：`regfix_ensure.sh`（root cron 每分钟）自动完成锚点解析 → `insmod mode=1` → 校验 → `rmmod`（映射有意保留）。
- 修复后**第一次运行** AVE 就成功编出 60 帧标准码流 ⇒ **冷启动即可用**。
- 同时确认：`omx_autodeploy`、云手机三件自愈脚本均正常工作（`/dev/amvenc_avc`、`/dev/jpegenc` 均按时上线）。

### 4.2 ⚠️ 两次非计划复位的真实原因（我方测量方式，非 AV 驱动缺陷）

| 时间    | 起因                                         | 说明                                                |
| ----- | ------------------------------------------ | ------------------------------------------------- |
| 08:37 | 我把 **3.7 GB** 4K 解码输出写进 **1.8 GB 的 tmpfs** | 内存压力 → zram 交换抖动 → 看门狗复位（kern.log 无 OOM 记录，硬复位特征） |
| 08:46 | 生成 4K 测试源（x264 4K 编码）时内存压力                 | 同上                                                |

- **不是硬解/硬编缺陷**：同期内 4K 解码本身 `rc=0`、输出完整；AVE 编解码全程正常。
- 已把口径改为：4K 只用 25 帧小样本、输出走 `/dev/null`、每步加内存守卫（`MemAvailable < 400 MB` 即中止）。
- 设备侧云手机服务**自愈正常**（webrtc-signalin 8443 在线）。

### 4.3 ⚠️ 端口转发隧道重启后未自启 ⇒ 公网 SSH 暂不可用

- 现象：`<RELAY_HOST>:<RELAY_PORT>` 连接被拒（隧道服务端在线、客户端未起）；局域网 `<LAN_IP>:22` 正常。
- 影响：远程运维需改走 **局域网**或 **NAS 自带的公网 Web 入口**（`<NAS_WEB_URL>`）。
- 这是既有已知问题（非本轮引入），**需手动恢复**（见第七节）。

### 4.4 🔧 修掉一个自愈脚本缺陷（已上线验证）

`regfix_ensure.sh` 原用「dmesg 行号切片」抓取 insmod 输出；当日志风暴遇上环形缓冲轮转时切片会**抓空**，导致误报  
`ERR regfix did not report FIX OK (matches=0)`（实际修复早已生效，无任何危害）。  
已改为**内核时间戳水位**（`MARK_TS + awk 过滤`），并加「抓空即 dump 最近 20 行 OESP_REGFIX 供人工判读」。  
验证：守卫静默（日志零增长）、`FORCE=1` 重跑 **OK matches=3**、随后正常路径再静默。

## 七、建议的下一步（按优先级）

1. **恢复远程通道**：在设备上把端口转发客户端拉起来（应用面板启动，或 `<TUNNEL_APP_PATH> start`），恢复公网 SSH；期间可用局域网或 NAS 自带 Web 入口。
2. **推开内核 QP 这道门**（AVE 编码真正可用的关键）：反汇编 `encoder.ko` 的 `FASTGX_AVC_IOC_NEW_CMD` 处理链，看 `control_info[6]`（quant）在哪一步被丢弃或未写入硬件寄存器；若仍是「剥坑」式改造（与 `registers.ko` 同款手法），有望像 codec-io 一样**运行时补齐**。
3. **零拷贝解码→编码/显示管线原型**：`vdec` 输出缓冲直接映射给编码器或渲染器，省掉每帧 3.1 MB 的用户态拷贝 —— 目标是消掉硬解的**双模态抖动**并再降 CPU。
4. **硬解稳定性追因**（低成本）：在容器负载低谷复测，确认双模态档位由 CMA 分配还是 CPU 竞争决定；若属后者，可在 `oesp_gpu_fix.sh` 增加「解码时降低容器优先级」的运维手段。
5. **GPU 控制台补 AV 性能面板**：把本报告的实测口径做成可点按钮（解码/编码一键基准），让性能变化可被周期观测。

## 八、⚠️ 口径修正（2026-10-08 傍晚复测，**以本节为准**）

### 8.1 触发与结论
复测硬解是否仍为正收益时发现：**第二~四节的「双模态抖动」是测量工具的假象，不是器件性能问题**。真实解码速率恒定，且此前三条结论需作废。

### 8.2 根因（已定位到源码行）
`vdec-dec` 源码（`vdec_test3.c`）的退出判据：
```c
g_expect = au_count - g_drop_init - g_tail_au;      /* 302-1-1 = 300 */
if (g_expect > 0 && frames >= g_expect) idle = 150;  /* 帧数达标: 只等 150ms */
else idle = stop_sent ? g_drain_ms : g_idle_ms;      /* 未达标: 回退 DRAIN_MS */
```
`g_drain_ms` 默认 **5000ms**。**固件偶发少吐 1 帧**（实收 299 < 预期 300）⇒ 退出等待从 150ms 变成 5000ms ⇒ **墙钟 ×3，算出的 fps 被腰斩**。

时间戳证据（逐行打点）：

| 现象 | `[drain]` 后停顿 | 实收帧数 | tool 用时 | 算出的 fps | core |
|---|---|---|---|---|---|
| 正常 | 2.00–2.04s（20 次全一致） | 300 | 2.26s | 132 | 0.86 |
| 慢档 | **6.86s** | **299** | 7.12s | 40 | 0.03（空等）或 0.90（poll 空转）|

两种 CPU 签名（几乎不吃 CPU / 吃满一核空转）由 poll 是否返回 POLLOUT 决定 —— 都是同一个「白等 5 秒」。

### 8.3 修正后的实测（空载，6 核；硬解口径 `IDLE_MS=100 DRAIN_MS=100`）

| 分辨率 | 硬解 fps | 硬解 CPU | 软解→NV12 fps | 软解 CPU | 软解仅解码 fps | 硬/软吞吐 |
|---|---|---|---|---|---|---|
| 1080p | **132**（10/10 命中 131.6–132.6） | 0.86 核 | 120.8 | 4.10 核 | 201 | 硬解 **+9%** |
| 720p | **231**（5/5 命中 230.4–234.2） | 0.77 核 | 255.9 | 4.05 核 | 406 | 硬解 **−10%** |
| 4K | **≈36** | 0.05–0.07 核 | 32.9 | 4.49 核 | 54 | 硬解 **+10%** |

- 像素速率：硬解 1080p 274 / 720p 213 / 4K 298 Mpx/s；软解→NV12 250 / 236 / 273 Mpx/s ⇒ **吞吐基本打平（±10%）**。
- 正确性：1080p 前 40 帧 **BYTE_IDENTICAL**（Y_MAE=0），无损。
- **负载敏感性：6 核同级满载下硬解 132.2–133.1 fps，与空载完全一致**（core 由 0.86 降到 0.55–0.69，吞吐不受影响）。

### 8.4 作废的旧结论（本报告第 2.1 / 2.3 / 2.5 / 六-6 / 七-3 / 七-4 节）

| 旧结论 | 现状 |
|---|---|
| 「1080p 双模态 40/118 fps」 | ❌ 慢档是工具假象；真实恒定 **132 fps** |
| 「4K 软解更稳更快，硬解抖动大」 | ❌ 反了：硬解 36 > 软解 33 fps，且 CPU 几乎为零 |
| 「双模态根源 = 用户态拷贝吃 CPU，消抖需零拷贝管线」 | ❌ 成因是工具回退；零拷贝对**降 CPU** 仍有意义，但**不再是消抖必需项** |
| 「硬解吞吐快 1.3×」 | ⚠️ 修正为 ≈1.0×（打平）；硬解价值收敛为**省 CPU** |
| 「容器抢 CPU 导致硬解掉速」 | ❌ 6 核满载零影响，归因不成立 |

### 8.5 待修（工程项）
`vdec-dec` 的退出判据应改为「连续无新帧 150ms 即退」（或把 `DRAIN_MS` 降到 ≤300），**消除 ~10% 会话的 3× 墙钟抖动**。这是 GPU 控制台解码服务可直接落地的改进。
