# OneThing Cloud OES Plus（Amlogic S922X）编解码能力评估

> 评估时间：2026-09-30 13:30–13:58
> 结论一句话：**有硬解，无硬编，能转码 —— 但转码应该用纯软件，不要走硬解。**

---

## 一、能力盘点

| 能力 | 有无 | 依据 |
|---|---|---|
| **H.264 硬解** | ✅ 有 | `meson-vdec` 驱动 + `/dev/video0`（meson-video-decoder），实测 720p 258 fps |
| 其他格式硬解 | ⚠️ 驱动支持，未验证 | 固件齐全：`g12a_h264/hevc_mmu/vp9`、`gxl_h263/h264/hevc/mjpeg/mpeg12/mpeg4_5/vp9`、`sm1_*` |
| **硬件编码** | ❌ **无** | 见下方三点证据 |
| 软件编码 | ✅ 全 | `libx264` `libx265` `libvpx` `libvpx-vp9` `mpeg4` |
| 软件解码 | ✅ 全 | ffmpeg 完整解码器 |
| **转码** | ✅ 能 | 实测 720p 62 fps / 1080p 39 fps（libx264 veryfast） |

### 为什么判定"没有硬件编码"（三点证据）

1. **V4L2 只有两个节点，都是解码器**
   ```
   video0  -> meson-video-decoder     (开源 meson-vdec，我们补的模块)
   video26 -> aml-vcodec-dec          (厂商闭源，禁碰)
   ```
   没有任何 `encoder` 类节点。

2. **厂商驱动目录里全是 `amvdec_*`（解码），没有一个 `amvenc_*`**
   `/lib/modules/6.18.18.c997-trim/updates/trim/amlogic-gx-vendor-drivers/` 下：
   `amvdec_av1 / avs2 / avs3 / h264mvc / h265 / h266 / mavs / mh264 / mmjpeg / mmpeg12 /
   mmpeg4 / vc1 / vp9 / ports ...`
   唯一带 enc 的 `encoder_common.ko`，`modinfo` 描述是
   **"AMLOGIC Video Encoder *Bug Report* Driver"** —— 它是调试上报驱动，不是编码器。

3. **固件目录只有解码固件**
   `/lib/firmware/meson/vdec/` 全是 `*_h264/hevc/vp9/mpeg*/mjpeg*.bin`，没有任何 encoder 固件。
   设备树也只有 `video-decoder@ff620000`，没有 encoder 节点；无 `/dev/amvenc*`。

> ffmpeg 虽然列了 `h264_v4l2m2m` / `hevc_v4l2m2m` 等**编码器**，但那只是通用的
> "V4L2 mem2mem 编码器封装"，**本机没有可供它打开的编码设备节点**，实际不可用。

## 二、实测性能（数据来自本机，非估算）

### 1. 纯硬解吞吐（vdec-dec → /dev/null，排除磁盘 IO）

| 分辨率 | 帧数 | 耗时 | 吞吐 | CPU | 像素吞吐 |
|---|---|---|---|---|---|
| 1280x720 | 500 | 1.970 s | **254 fps（10.2x 实时@25fps）** | 83%（0.8 核） | 234 Mpx/s |
| 1920x1080 | 250 | 1.949 s | **128 fps（5.1x 实时@25fps）** | 80%（0.8 核） | 266 Mpx/s |

> 1080p 此前是推算（≈84 fps），重启后实测补上，**比推算高 52%**。
> 两次连跑 1.952 / 1.949 s，误差 <0.2%，数据可信。
> 硬解能力本质上是**像素速率受限（约 230–270 Mpx/s）**，与分辨率无关：
> 720p×500 帧（460 Mpx）和 1080p×250 帧（518 Mpx）耗时几乎相同。

### 1b. 硬解 vs 软解 CPU 对比（验收器实测）

| | 硬解 | 软解 |
|---|---|---|
| real720 解码 CPU | **0.60 核** | 1.94 核 |
| 结论 | **省 3.2 倍 CPU** | |

### 2. libx264 纯编码速度（720p，250 帧，6 核全开）

| preset | 吞吐 | CPU |
|---|---|---|
| ultrafast | **184 fps** | 470% |
| veryfast | 80 fps | 417% |
| faster | 57 fps | 452% |
| medium | 44 fps | 468% |

### 3. 端到端转码（H.264 → H.264，crf 23）

| 方案 | 720p / 500 帧 | 1080p / 250 帧 |
|---|---|---|
| **全软（软解 + 软编 veryfast）** | **7.9 s（63 fps）CPU 375%** | **6.36 s（39 fps）CPU 444%** |
| 硬解（我们的 vdec-dec）+ 软编，管道 | 12.4 s | — |
| 硬解 + 软编，落盘中转 | 13.6 s | 14.3 s |

**关键结论：硬解 + 软编比全软慢约 55%。**

原因不是硬解不够快（258 fps 远超编码的 80 fps），而是**把帧交给 ffmpeg 的通道太贵**：
- 720p 帧 500 张 = 691 MB，落盘要写一遍再读一遍，管道要穿两次内核缓冲
- 实测硬解写盘那一趟 sys 时间从 1.47 s 涨到 6.34 s
- 而 ffmpeg 内部软解是**零拷贝**的：全软 8.0 s vs 纯编码 6.3 s，**软解只多花 1.7 s**

所以在这台 6 核 A53 上，转码的瓶颈 100% 在 libx264 编码，硬解省下的那点 CPU
抵不过帧搬运的开销。

## 三、该怎么用（推荐方案）

### 转码：纯软件，别用硬解

```bash
# 720p / 1080p 转码（H.264 → H.264）
ffmpeg -i in.mp4 -c:v libx264 -preset veryfast -crf 23 -c:a copy out.mp4

# 追求最快（约 7x 实时 @720p）
ffmpeg -i in.mp4 -c:v libx264 -preset ultrafast -crf 23 -c:a copy out.mp4

# 只换容器/剪切，不重编码（速度受磁盘限制，300 MB/s）
ffmpeg -i in.mkv -c copy out.mp4

# 1080p → 720p 降压（先缩放再编码，比先编码快）
ffmpeg -i in.mp4 -vf scale=1280:720 -c:v libx264 -preset veryfast -crf 23 out.mp4
```

实时性判断（25 fps 片源）：
- 720p 转码 63 fps → **2.5x 实时，绰绰有余**
- 1080p 转码 39 fps → **1.6x 实时，可以**
- 1080p 用 medium preset（约 22 fps）→ 略低于实时，别用
- **H.265 输出（libx265）会很慢**，A53 上 1080p 大概率个位数 fps，不建议

### 硬解的正确用途：纯解码场景

不转码、只要帧的时候，硬解才划算（258 fps，只用 1 核，软解要 2–3 核）：

```bash
ffmpeg -i in.mp4 -c:v copy -f h264 in.h264          # 先抽出 Annex-B 裸流
PRELUDE_AU=2 TAIL_AU=1 COMPACT=1 \
  vdec-dec /dev/video0 in.h264 0 out.nv12           # 硬解出紧凑 NV12

# 抽帧（每 25 帧取 1 张）
ffmpeg -f rawvideo -pix_fmt nv12 -s 1280x720 -r 25 -i out.nv12 \
  -vf "select='not(mod(n\,25))'" -vsync vfr thumb_%04d.jpg
```

适用场景：视频抽帧/缩略图、AI 分析喂数据、多路并发解码、播放器后端。

## 四、本轮踩坑（重要）

### 1. ⛔ 新增致命雷区：`ffmpeg -c:v h264_v4l2m2m` 硬解

**本次评估的收尾实验用它做"ffmpeg 内部硬解 + 软编"时，整机内核级死锁**——
ping 0/3、SSH 超时、无看门狗自愈。这是本设备**第三次**被搞挂。

> **死锁已二次确认**：后台跑 `final_bench.sh` 满 25 分钟无响应，远程执行客户端 读超时
> （`socket.timeout`）；重启前再探一次 22 端口，6 秒无 banner，**整机确实硬挂**，
> 不是脚本卡住。必须物理断电。

> 累计致命雷区（碰了就要物理断电）：
> 1. `/dev/video26`（闭源 aml-vcodec-dec）— open 即死锁
> 2. `/sys/class/vdec/*` 任何节点 — 只读 cat 即死锁
> 3. **`ffmpeg -c:v h264_v4l2m2m`（v4l2m2m 硬解）— 配合软编时死锁**
> 4. 运行时 `rmmod` 闭源 GPU 驱动（mali）

安全白名单：`/dev/video0` 的标准 V4L2 ioctl、`/sys/class/video4linux/video*/name` 只读、
`dynamic_debug`、`lsmod`/`dmesg`/`/proc/meminfo`、固件只读 `ls`/`md5sum`、
ffmpeg 软编解、`/root/vdec` 目录 IO。

### 2. 修掉了两个真实 bug（都会让数据失真）

- **`vdec-dec <dev> <流> 0 <输出>` 传 0 会一帧都不解**。`max_frames=0` 时
  `while (frames < 0)` 立即退出。已改为 `<=0` 视为不限。
  （之前验收器传的是具体帧数，所以一直没暴露。）
- **drain 后空等 5 秒**。`g_drain_ms` 默认 5000，取完帧还要干等 5 s 才退出，
  导致"解码耗时"被恒定 +5 s 污染（同一片源 1.82 s vs 6.83 s 的差异全在这里）。
  已加"预期帧数"判据：达到 `au_count - 丢弃 - 尾部追加` 后只等 150 ms。

### 3. `max_frames` 传 0 之外，还有一个数字陷阱

早期版本把 OUTPUT 缓冲设成 4 MB × 16 个 = 64 MB，CMA 不够（本设备 CMA 总量 1.18 GB，
**空闲常只剩 ~270 MB**），驱动只批了 2 个 buffer，表现为
"**码流只送进去 2 个 AU 就停**"。已改为 2 MB × 8 个并加自适应降级（不足则减半重试）。

## 五、重启后要做的事

1. **物理断电重启**（本次死锁无自愈）。
2. 一键复核（已写好脚本，只走安全白名单）：
   ```bash
   # 本地
   python run_many.py post_reboot_check.sh vdec_test3.c,hwdec_verify.py 900
   ```
   脚本会依次做：系统唤醒确认 → `modprobe meson-vdec` → 重编译 `vdec-dec` →
   `hwdec-verify --quick` → **补测干净的 1080p 硬解吞吐**（跑 2 次取稳定值）→
   720p 对照 → 清理 `/tmp`。
3. **不要再试** `ffmpeg -c:v h264_v4l2m2m`。

## 六、重启后复核结果（已全部跑完）

**设备完全没被第三次死锁搞坏。** `modprobe` 后 `/dev/video0` 正常，
`hwdec-verify --quick` **13/13 全过**，正确性仍是 **Y_MAE=0.00 / PSNR=99.00 dB
（与软解逐字节相同）**，端到端 mp4 moov 完整，收尾无 D 状态卡死进程。

唯一小瑕疵：`band720` 取回 38/40（尾部少 2 帧），在容差 3 内判 PASS。
尾部丢帧是**固定常数**（1–3 帧）而非按比例，见第六轮报告。

> 注意一个数字：重启后 **CMA 空闲只剩 27 MB**（总量 1.18 GB）。
> 闭源驱动预占绝大部分，但解码仍正常跑满 —— 说明 meson-vdec 实际用的
> CMA 远小于我们早期担心的量，不必为此紧张。
