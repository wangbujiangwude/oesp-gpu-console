# 真实播放器硬解打通报告（OMX + ByteBuffer + 框架软渲染器）

时间：2026-10-04 02:0x · 设备：OESP（S922X / G12B）· 容器 androidemu-android

---

## 一句话结论

**已打通。** 通过在 OMX 插件里回答 `OMX_IndexParamVideoAndroidRequiresSwRenderer = 1`，
让 ACodec 放弃 ANW/Surface 输出、改用**已验证的 ByteBuffer 模式**，再由框架自带的
`SoftwareRenderer` 把 NV12 画到 Surface。系统播放器/相册现在**真正跑硬件解码**，画面正确。

---

## 1. 根因（为什么之前"任何真实播放器都用不了硬解"）

框架 `ACodec.cpp`（"determine need for software renderer" 段落）的判定顺序：

```cpp
if (haveNativeWindow) {
    status_t err = mOMXNode->getParameter(
            (OMX_INDEXTYPE)OMX_IndexParamVideoAndroidRequiresSwRenderer, &param, sizeof(param));
    if (err == OK && param.nU32 == 1) requiresSwRenderer = true;

    if (mComponentName.startsWith("OMX.google.") || requiresSwRenderer) {
        usingSwRenderer = true;
        haveNativeWindow = false;
        setPortMode(kPortIndexOutput, IOMX::kPortModePresetByteBuffer);   // ← ByteBuffer
    } else if (!storingMetadataInDecodedBuffers()) {
        err = setPortMode(kPortIndexOutput, IOMX::kPortModePresetANWBuffer);
        if (err != OK) return err;                                       // ← 直接失败
    }
}
```

- 我们的组件原来对这个索引**返回不支持** → `requiresSwRenderer = false`
- 于是框架走 `kPortModePresetANWBuffer`（要求解码器直接把结果写进 gralloc/Surface 缓冲）
- 我们的组件只有 ByteBuffer 能力 → `setPortMode ... failed w/ err -1010` → **组件被销毁、回退软解**

实测 ACodec 查询的索引值就是 **`0x6F600011`**（日志 `GetParameter index=0x6f600011` 可证）。

> 顺带排除了"gralloc 不能 CPU 写"这个次要障碍：容器 gralloc 虽能 lock 自建缓冲，
> 但 ACodec 下发的 ANW 缓冲 `AHardwareBuffer_lock` 恒返回 `-38 (INVALID_OPERATION)`，
> 说明这条 CPU 直写路径在容器里本来就走不通 —— 所以 **ByteBuffer + 框架软渲染器才是正解**。

## 2. 改动（`omx-meson/meson_omx_plugin.cpp`，共 1 处新增）

```cpp
case OMX_IndexParamVideoAndroidRequiresSwRenderer: {
    OMX_PARAM_U32TYPE *p = (OMX_PARAM_U32TYPE *)pParamStructure;
    p->nSize                    = sizeof(*p);
    p->nVersion.s.nVersionMajor = 1;
    p->nPortIndex               = kOutputPortIndex;
    p->nU32 = propInt("debug.meson.swrenderer", 1) ? 1u : 0u;   // 默认开，可 setprop 关
    LOGI("RequiresSwRenderer -> nU32=%u", p->nU32);
    return OMX_ErrorNone;
}
```

同时把 `GetExtensionIndex` 里对 `useAndroidNativeBuffer2` 的声明去掉（强制框架走老路径），
ANW 相关分支保留但不启用。

**开关**：`setprop debug.meson.swrenderer 0` 可退回尝试 ANW（调试用）。

## 3. 验收（全部实测）

### 3.1 框架路径确认

```
MesonOMX: RequiresSwRenderer -> nU32=1 (1=ByteBuffer+软渲染器, 0=尝试 ANW)
MesonOMX: 接受 ANW 缓冲（port=1）            ← 框架先探了一下，随后被 SwRenderer 分支覆盖
MesonOMX: [dec] CAPTURE 就绪: 1280x720 ...
MesonOMX: [dec] 输出第 1 帧, 1382400 字节 (1280x720 stride=1280)
MesonOMX: [dec] 输出第 100 帧
MesonOMX: [dec] 输出 EOS（共 100 帧）
```

### 3.2 硬件解码确实在跑

| 指标 | 数值 |
|---|---|
| 宿主 `vdec` 中断 | 播放前 693 → 播放中 **稳定 23 次/秒** |
| 解码帧数 | 100/100（短片）、650/持续增长（84 秒长片） |
| 画面 | 截图为标准 720p 彩条 + 时码「720P 60:00:00:00」，**无 UV 错位、无绿屏** |

### 3.3 端到端 CPU（84 秒 720p，系统相册播放）

容器 6 核（总 600%），播放期间 `top` 最高进程 **24%**、多数为 0～8% ——
720p 播放占用不到一个核的零头。

对比参考（同一 mctest，仅换组件名）：

| | meson（硬解） | google（软解） |
|---|---|---|
| 720p 100 帧 CPU | **0.72s** | 1.22s |

即解码侧 CPU 省 **41～46%**，且现在路径是真实播放器路径（不再是孤立的 ByteBuffer 测试）。

### 3.4 无回归

`mctest /sdcard/Movies/hwtest.mp4 100`（不指定组件、无 Surface）→ 100/100 帧、`rc=0`。
说明无 Surface 的纯 ByteBuffer 场景完全未受影响。

## 4. 仍然用不上硬解的两个场景（都是 App 自身策略，不是我们的问题）

| 应用 | 现象 | 原因 |
|---|---|---|
| **VIA / Chromium 内核浏览器** | logcat 明确 `decoder name OMX.google.h264.decoder` | Chromium 主动 `requireSoftwareCodec`，按自己的白名单/能力判定走软解；除非它自己开"硬件加速"开关，或我们额外声明 `COLOR_FormatSurface` |
| **抖音** | 线程 `VDecod2-V1/V2`，加载 `libttffmpeg.so` + `libvideodec.so`，`/dev/video0` 打开数 **0** | 抖音走自研 TTMediaPlayer + 自带 ffmpeg 解码，**全程不调用 MediaCodec**（logcat 里一条 MesonOMX 都没有） |

> 抖音这条需要单独查：确认它是不是因为流是 HEVC（G12B 无 HEVC 硬解）而干脆不用 MediaCodec。
> 建议进一次抖音直播间，我实时采样再定论。
