# Amlogic 厂商解码栈开盖报告（2026-10-05）

> 设备：OESP / Amlogic S922X (G12B)，飞牛 fnOS 内核 `6.18.18.c997-trim`
> 触发问题：同款芯片的电视盒子宣称 4K@75fps 全格式硬解 + 1080p@60 硬编，
> 为什么飞牛做不到？能不能把电视盒子的驱动逆向移植过来？
> 方法：**全部静态取证**（读文件 / `modinfo` / `strings` / `ls`），
> **未 open 任何危险设备**，全程零风险。

---

## 〇、一句话结论

**不需要"逆向移植"—— 电视盒子那套驱动飞牛已经移植好了，就在系统里，而且编译进了当前内核。**
真正的问题是：**飞牛官方主动把它关掉了，我们此前也一直没发现它，而在社区驱动上白做了一轮优化。**

## 二、为什么它没被启用：飞牛自己关的

```
$ cat /etc/modules-load.d/meson-vdec.conf
# meson-vdec  # 禁用: 帧回传会挂死驱动

$ cat /etc/modules-load.d/trim-amlogic-gx-vendor-drivers.conf
galcore
```

**飞牛官方的注释直接写明：帧回传会挂死驱动。**
这与本项目记录的雷区 #1（`/dev/video26` open 即整机死锁）是同一件事。
官方的选择是：厂商栈留着但不启用，改走 `galcore`（Vivante GPU）。

### 当前加载状态（driver 绑定）

| driver | 绑定设备 | 状态 |
|---|---|---|
| `aml-vcodec-dec` | `vcodec-dec` | ✅ probe 成功（`/dev/video26` 由此而来） |
| `codec_mm` | `codec_mm` | ✅ probe 成功 |
| `mesonstream` | `mesonstream` | ✅ probe 成功 |
| `meson-vdec` | `ff620000.video-decoder` | ✅ probe 成功（`/dev/video0`，我们用的） |
| `amvenc_avc` | （空） | ❌ DT 无节点，未 probe（硬编） |
| `vdec` | （空） | ❌ vdec-legacy 未绑定 |

即：**框架活着，具体格式解码器一个都没挂上。**

### 格式模块怎么被拉起

`amvdec_ports.ko` 内置了全套 V4L2 接口层（源码路径可见）：

```
amvdec_ports/decoder/vdec_hevc_if.c    vdec_av1_if.c     vdec_avs2_if.c
vdec_avs3_if.c    vdec_h266_if.c       vdec_vc1_if.c     vdec_mpeg12_if.c
vdec_mpeg4_if.c   vdec_mjpeg_if.c      vdec_h264_if.c
```

而 `decoder_common.ko` 内含 `amvdec_h265`、`amvdec_av1`、`amvdec_avs2`… 等模块名字符串，
说明具体解码器由 **按需 `request_module` 动态加载** —— 
**因为从来没人真正 open 设备并请求解码，所以它们一直没被加载。**

## 三、厂商栈 vs 社区栈：差距在哪

| 维度 | 社区 `meson-vdec`（`/dev/video0`，在用） | 厂商 `amvdec_ports`（`/dev/video26`，未启用） |
|---|---|---|
| 格式 | H.264 / VP9 / MPEG1 / MPEG2（4 种） | **H.264 / HEVC / AV1 / AVS2 / AVS3 / VP9 / VC1 / MPEG4 / MJPEG / H.266** |
| 内存管理 | 通用 CMA + `videobuf2-dma-contig` | **`codec_mm`（Amlogic 私有池）+ dma-buf** |
| 后处理 | 无 | **VPP（视频后处理）+ ge2d（色彩/缩放硬件）** |
| 输出 | NV12 回 CPU（uncached，慢） | **`enable_drm_mode` 走 DRM dma-buf，零拷贝** |
| 编码 | 无 | `encoder.ko` / `jpegenc.ko` |
| 微码 | 逐格式单独加载 | `video_ucode.bin` 统一 ucode |

`amvdec_ports` 的关键参数（说明它支持什么）：

```
bypass_vpp / bypass_ge2d / disable_vpp_dw_mmu / enable_drm_mode / multiplanar
aml_set_vdec_type / aml_set_vdec_type_enable / param_sets_from_ucode
dump_capture_frame / dump_vpp_input / dump_ge2d_input / dump_output_frame
```

**这就是电视盒子能做到 4K@75 的原因**：VDEC → VPP → ge2d → DRM 全程硬件，CPU 不碰像素。

## 四、回头看：为什么我们的硬解是负收益

此前实测（真实播放器，720p@25）：硬解 **1.39~1.49 核** vs 软解 **0.86~0.88 核**。
而 `mctest` 纯解码（无渲染）：硬解 0.72s vs 软解 1.22s，**硬解省 41%**。

矛盾的解释现在很清楚了：

```
社区栈：VDEC → NV12(uncached CMA) → [CPU memcpy] → OMX IL → [CPU YUV→RGB] → 上屏
                                     ↑ 这两步吃掉全部红利并倒挂

厂商栈：VDEC → VPP → ge2d → DRM dma-buf → 上屏       （CPU 不参与）
```

三项代码级优化（整块 memcpy、零拷贝旁路、空闲等待）实测**全部无效**，
正是因为**瓶颈不在我们改得动的用户态，而在"帧必须回 CPU"这个架构选择上**。
这也解释了飞牛那句注释 —— "帧回传会挂死驱动"说的就是同一段路。

## 五、三个问题的答案

### 问题 1：VDEC 解码收益还要哪些优化？

**在社区栈上已经没有优化空间了**（三项实测无效已证伪了用户态路径）。
真正的优化只有一个：**换栈到厂商 `amvdec_ports`**，用它的 VPP + ge2d + DRM 链路，
让帧根本不回 CPU。附带收益：硬编、`vc8000`、`vpu`、`media_sync` 一并解锁。

### 问题 2：至少要让硬解 CPU 低于软解

**可行，但必须换栈。** 厂商栈本来就是电视盒子的量产方案，
在 `enable_drm_mode` + VPP/ge2d 不 bypass 的配置下，理论上 CPU 占用应接近零拷贝水平。
研究路径上的硬障碍：`/dev/video26` **open 即整机死锁**，且本机**无硬件看门狗**，
一旦触发只能物理断电。

### 问题 3：增加格式 + docker 层统一解码器调度

- **格式**：不需要写驱动，`modprobe amvdec_h265` / `amvdec_av1` / `amvdec_vp9` / … 即可，
  45 个模块现成，微码齐备。
- **docker 层统一调度**：厂商栈的 `codec_mm` 是**全局内存管理器**，
  天生适合多容器共享；可设计一个宿主侧 `vdecd` 守护进程统一持有解码会话，
  容器通过 socket / dma-buf fd 转发，天然解决"不同 App 各调各的解码器、
  占用高还容易报错"的问题。社区栈目前只能靠 `flock` 做会话互斥（已实现），
  换栈后可升级为真正的集中调度。

## 六、⛔ 风险与前置条件（必须先看）

| 风险 | 说明 |
|---|---|
| **整机死锁** | `/dev/video26`（`aml-vcodec-dec`）open 即死锁，无看门狗，需**物理断电** |
| 无 `/dev/watchdog` | 已确认本机无硬件看门狗，内核硬死锁时软看门狗同样失效 |
| 模块加载风险 | `modprobe amvdec_h265` 等会在 init 中操作硬件，可能直接触发死锁 |
| 影响面 | 死锁会影响宿主 + 全部容器（含正在跑的 androidemu、云手机） |

**建议的分步验证协议**（每步单独执行、单独确认，不做批量）：

1. 先停掉安卓容器等重负载业务，缩短断电损失窗口
2. `modprobe` 一个**最保守**的格式模块（如 `amvdec_mmpeg12`），观察 60 秒
3. 若存活 → 依次试 `amvdec_mh264` → `amvdec_h265`
4. 全程**不 open `/dev/video26`**，直到确认格式模块加载稳定
5. 用 `amvdec_ports` 的 `debug_mode` 参数 + `dynamic_debug` 取日志，不靠 open 试
