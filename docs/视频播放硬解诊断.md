# VIA 播放视频：这是硬解吗？—— 诊断报告

时间：2026-10-04 00:5x · 设备：OESP（S922X/G12B）· 容器 androidemu-android

## 直接回答

**不是硬解。** 而且当前**任何真实播放器（浏览器 / 抖音 / 系统相册）都用不上硬解** —— 根因不在浏览器，在我们的 OMX 插件缺少 Surface 输出能力。

判据（你截图里就能看到）：
- **VDEC 硬解负载 0.00/s** —— 解码器一次都没工作
- **3D GPU 132 job/s** —— 这是**渲染**（软解出画面 → 上传 GPU 纹理 → 合成显示），跟解码无关
- GPU 频率 250MHz、job 中断 33896 —— 都是渲染侧指标

## 现场抓到的证据

### 证据 1：VIA 主动要了软解
```
cr_MediaCodecBridge: create MediaCodec video decoder, mime video/avc,
                     decoder name OMX.google.h264.decoder
```
`OMX.google.h264.decoder` 是 Google 的**纯软件**解码器。VIA 进程 fd 里 `renderD128 ×6 / video0 ×0` —— 没碰硬解。

Chromium 内核的选码逻辑（读过源码）：普通视频走 `createDecoderByType()`，但一旦判定要走软解，
就用 `getDefaultCodecName(requireSoftwareCodec=true)` —— 该函数用 `isSoftwareCodec()` 过滤，
我们的组件 `isHardwareAccelerated()=true` → 被跳过；Google 的命中 `omx.google.` 前缀 → 选中。
**这是浏览器的策略选择，我们改不了**（除非 VIA 设置里有"硬件加速"开关）。

### 证据 2：系统播放器想用 meson，被 ANW 挡回（关键）
我用系统播放器播同一个 H.264 文件（720p，mctest 验证过能硬解），插件日志：

```
MesonOMX: makeComponentInstance(OMX.meson.h264.decoder)
MesonOMX: GetExtensionIndex(OMX.google.android.index.enableAndroidNativeBuffers)
MesonOMX: 拒绝 ANW 缓冲（port=1）-> 走 CPU 缓冲 + 软渲染
MesonOMX: ANW/native-handle 相关扩展不支持 index=0x6fa00008
ACodec  : [OMX.meson.h264.decoder] setPortMode on output to DynamicANWBuffer failed w/ err -1010
ACodec  : [OMX.meson.h264.decoder] setPortMode on output to PresetANWBuffer failed w/ err -1010
MesonOMX: destroyComponentInstance
MesonOMX: ComponentDeInit（输出 0 帧）
```

框架**正确选中了 meson**（说明组件注册、优先级都没问题），但真实播放器必须让解码器
**直接输出到 Surface（ANW buffer）**；我们返回不支持 → ACodec 只能销毁组件 → 回退软解。

插件源码里的对应位置（`omx-meson/meson_omx_plugin.cpp`）：
```cpp
case kIdxEnableAndroidNativeBuffers: {
    ...
    // 本阶段不支持 gralloc/ANW 缓冲；返回让框架回退到 CPU 缓冲
    LOGI("拒绝 ANW 缓冲（port=%d）-> 走 CPU 缓冲 + 软渲染", port);
}
case kIdxGetAndroidNativeBufferUsage:
    p->nUsage = 0;   // 不支持 ANW，usage 无意义
```

## 结论修正

| 之前的说法 | 修正后 |
|---|---|
| "抖音 CPU 高是 VDEC 卡死导致回退软解" | **不准确**。即使 VDEC 正常，抖音（走 Surface）也用不了 meson 硬解，同样回退软解 |
| "OMX 组件已打通，App 可直接受益" | 只对 **ByteBuffer 模式**成立（mctest 验证的就是这个）；**真实播放器全走 Surface → 全部用不了** |

VDEC 重启恢复本身是成功的（vdec 中断 0→99，mctest 100/100 真实硬解帧），
但它只证明了"解码器能工作"，没证明"播放器能用它"。

## 下一步（要真正让播放器用上硬解）

**必须给 OMX 组件实现 ANW / Surface 输出**，也就是让解码结果直接进 gralloc buffer：

| 阶段 | 内容 | 难度 |
|---|---|---|
| ① 最小可用 | `enableAndroidNativeBuffers` 返回 OK，`getAndroidNativeBufferUsage` 给出 GRALLOC_USAGE_HW_VIDEO_ENCODER 等，`useAndroidNativeBuffer` 时用 ANativeWindow 分配 buffer，把 VDEC 输出 memcpy 进 ANW | 中 |
| ② 零拷贝 | VDEC 输出的 dma-buf 直接导出给 ANW（`SetParameter` 的 `AndroidNativeBufferInfo`），省掉那次拷贝 | 高 |
| ③ 浏览器 | VIA 若要硬解还得它自己开硬件解码开关；Chromium 侧不检查 ANW，只要组件被框架选中就会用 | — |

另外发现一个次级问题：**连 Google 软解也报**
`[OMX.google.h264.decoder] setPortMode on output to DynamicANWBuffer failed w/ err -1010`
说明容器内 ANW/gralloc 到 Surface 这条链路本身也有瑕疵（可能是 gralloc=gbm + mesa 下的兼容问题），
实现 ANW 前建议先把这条链路查通。
